# 모델·위임·토큰 적용 점검

2026-11-14. 현재 R02 아트 통합/R03 저장 작업의 실행 기록을 점검했다. 이 문서는 설정 계획과 실제 적용을 구분하며 비용·절감률을 추정하지 않는다.

| 항목 | 실제 관측 | 한계 |
| --- | --- | --- |
| 역할 분리 | Claude 아트 담당, Codex Unity 구현, 별도 코드/PC 시각 리뷰, 순수 저장 구현·독립 리뷰 | 역할 분리가 모델별 비용 최적화를 입증하지 않는다 |
| 모델 지정 | 최근 자체 subagent 호출은 부모 모델 상속, 모델/effort override 없음. Orca 후속 요청은 기존 worker 재사용 | 경량/표준/고성능을 과업별로 실제 전환했다는 근거가 부족하다. 정확한 호출별 실제 모델은 미확인 |
| 문맥 전달 | 파일 allowlist·명시 인계·같은 구현자/리뷰어 재사용 | 최근 자체 subagent는 전체 대화 상속을 사용해 문맥 전달 비용 개선 여지가 있다 |
| 검증 비용 | 좁은 거절 검사와 자동 검증 도구 재사용, 수정 후 관련 회귀·변이·최종 결속 | 저장 결함의 반복 발견으로 추가 구현/검토가 발생했다. 품질 검증 비용을 절감으로 계산하지 않는다 |

## 이후 배정 규칙

사용자가 말한 용도는 파일 탐색/정보 추출/구현/검증 판단 같은 작업 단위다. 아래는 다음 새 위임에서 적용할 후보 매핑이며 과거 호출의 실제 모델을 뜻하지 않는다.

| 작업 | 실행 기준 |
| --- | --- |
| 파일명·문자열 찾기/정해진 검사 실행 | 먼저 rg/스크립트. 모델 호출이 추가로 필요한 여러 파일 탐색·근거 추출은 gpt-6-luna/low 후보 |
| 범위가 정해진 코드 구현·일반 회귀 시험 작성 | gpt-6.1-sol/medium 후보 |
| 일반 리뷰·설계·오류 분석 | Sol 우선. 위험도가 높다는 이유만으로 Astra를 자동 배정하지 않음 |
| 어려운 검증 또는 Sol로 해결하기 어려웠던 문제 | 사용자 지정 Astra 사용 조건. 실패 접근/남은 판단과 필요한 근거를 좁혀 gpt-6-astra/high 후보 검토 |
| 아이디어 발상 | Sol 기본. 아이디어라는 이유만으로 Astra 자동 배정하지 않음 |
| 반복 실행·해시·픽셀 계산·합격 조건 확인 | 결정적 도구 우선. 의미 해석이 필요한 경우에만 해당 위험 계층의 모델 호출 |

단순 검색마다 새 worker를 만드는 비용은 피한다. 가용 모델/effort와 실제 호출 지정 가능성을 확인하며, 현재 부모 턴을 작업마다 자동 교체했다고 주장하지 않는다. 위임 시 필요한 경로와 근거만 전달하고 실제 호출 지정값을 남긴다.

- 짧은 조회·상태 정리·포맷 작업은 coordinator가 직접 처리한다. 별도 worker가 필요한 좁은 저위험 작업에만 가용 경량 후보를 검토한다.
- 일반 C#/Unity 구현·설계·리뷰는 Sol을 우선한다. 사용자 최신 지시대로 Astra는 어려운 검증 또는 Sol로 해결하기 어려웠던 문제에만 사용한다. 실제 호출 옵션과 가용성을 확인한 후 지정하고 선택 프로필과 실제 모델을 별도 기록한다. 미지정/상속도 숨기지 않는다.
- 새 자체 worker는 독립 작업에 필요한 파일·계획·근거 경로만 전달하는 짧은 문맥을 우선한다. 기존 담당자의 후속 수정/재검토는 같은 세션을 재사용한다. 실행 중인 작업의 모델을 바꾸거나 같은 작업을 새 worker에 중복 배정하지 않는다.
- 실제 usage를 받을 수 있으면 원본 근거와 함께 기록하고, 없으면 null/미측정으로 둔다. baseline과 완전한 총량 없이 절감률을 발표하지 않는다.
- 전역 모델·계정·과금 설정은 변경하지 않는다. 사용자 지정 Claude Design 제품과 Claude worker/스크립트 제작을 서로 대신했다고 기록하지 않는다.

현재 이 개선 규칙은 이후 호출의 배정 기준이다. 과거 작업에 소급해 모델 전환·토큰 절감 실적으로 기재하지 않는다. 구체 모델 후보/선택·재시도 기준은 전용 skill의 `references/model-routing.md`를 따른다.

## 첫 적용: P2 캡처 측정

사용자가 구현 담당 채팅에서도 용도별 모델·토큰 최적화·멀티에이전트를 명시 승인했다. 담당자는 P2의 독립된 캡처 측정만 최소 문맥의 helper에 `gpt-6-luna`/`low`로 지정했다고 보고했다. 제품/Editor/GUI 소유는 Unity 구현자 한 명이 유지하며 helper는 제품을 편집하지 않는다. 이는 worker 보고에 따른 **호출 지정값**이며 실제 응답의 resolved model·usage 원문은 아직 root가 확인하지 않았다. 사용량은 미측정, 비용/절감률은 미계산이다. 구현자는 helper의 측정 결과를 검증한 뒤 최종 P2 근거에 호출 식별자·범위·지정/실제 모델 구분을 포함한다.

## 지속 측정 추가: 2026-11-15

root의 로컬 Codex 세션에서 실제 `token_count` 누적 집계를 확인했다. 과거 미측정 기록을 소급해 프로젝트 총비용으로 바꾸지 않는다. 해당 세션은 과거 대화도 포함하므로 첫 관측은 기준점만 기록한다.

`tools/record_model_usage.py`는 지정한 한 세션의 token event와 model 필드만 읽어 ignored `evidence/model-usage/checkpoints.jsonl`에 단계/결과·관측 시각·입력/캐시읽기/캐시쓰기/출력/추론/기존 total 및 이전 기준점과 차이를 남긴다. 원문 프롬프트/응답은 수집하지 않는다. reasoning은 output에 포함될 수 있으므로 더하지 않는다. counter 감소는 reset/incompatible로 표시하고 차이를 합산하지 않는다. 사용량 없는 로그는 명시 실패하며0으로 채우지 않는다.

단계 시작/끝에 `python3 tools/record_model_usage.py --phase <단계> --checkpoint start|end --result PENDING|PASS|FAIL|NOT_RUN`을 실행한다. worker도 자기 session ID로 별도 기록해야 전체 합산이 가능하다. 등록되지 않은 worker가 있으면 총량 불완전이다. 현재 진행 중인 호출은 마지막 token event 이후라 집계에서 빠질 수 있으므로 event 시각을 보존한다. 세션 구간에는 대화/조율도 들어가며 제품 작업에만 귀속된 비용으로 발표하지 않는다.

실제 청구액은 제공되지 않아 null이다. API 환산도 요청별 모델·서비스 tier·긴 문맥 할증·검증된 단가를 모두 적용할 근거가 없으면 null로 둔다. 현재 단가의 공식 근거는 [API pricing](https://developers.openai.com/api/docs/pricing)와 [Sol 모델 조건](https://developers.openai.com/api/docs/models/gpt-6.1-sol)이다. 구독 청구액을 API 단가로 계산했다고 표현하지 않는다.

각 단계 GC에서는 성공 여부/수정 회수/실패 접근·검증 범위와 이 구간 측정을 함께 비교한다. 같은 수용 기준의 baseline이 확보될 때만 개선 성과를 판단하며, 짧은 문맥/worker 사용 사실만으로 절감률을 계산하지 않는다.
