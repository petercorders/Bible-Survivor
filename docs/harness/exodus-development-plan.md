# 출애굽기 제작 계획 1

2026-11-17. 사용자 “챕터2 출애굽기를 챕터1처럼 진행” 요청과 기존 지속 승인으로 시작. 현재 산출물은 `../exodus-balance.md`의 6라운드 **기획 초안**이다. 이번 문서 작성만으로 게임·카탈로그·저장이 확장된 것은 아니다.

사용자 후속 지시 “15까지도 계속 구현 진행해줘야지”에 따라 전체 실행 범위는 **R10~R15 PC 구현·검증·독립 리뷰·라운드 GC·커밋/업로드**다. R10은 첫 중간 단위이며 완료 후 R11~R15 계획과 실행을 이어간다. 라운드별 재승인 대기나 새 Run 생성 없이 이 작업을 계속한다. R12/R15 보스 상세는 해당 단위에서 작성·검토하며, 유료 행동 외 기존 승인에 필요한 질문을 반복하지 않는다.

## 단계와 완료 조건

1. 기획: 인물별 초점1회·혼합3웨이브·누적3주기 보스·본문과 창작 분리. 6라운드안과 아론 압축/마지막 창작전투의 한계를 독립 검토한다. 콘텐츠 초안은 수치 카탈로그가 아니다.
2. 전환 설계 + R10: `AdamSession.ChapterComplete`, `TryAdvance`의9상한, `SaveState/SaveFormat`의 콘텐츠 상한·receipt allowlist, `AdamCatalog`의genesis고정, Host/UI의 콘텐츠 끝을 함께 설계한다. 단순히 모든9를15로 치환하지 않는다. chapter ID/local round/global number 대응과 기존 fingerprint를 보존한다. chapter1 완료와 전체 설치 콘텐츠 완료를 별도 개념으로 표현한다.
3. R10 수치·카탈로그/코어와 독립 아트 준비를 병렬 수행. 전환 원자성, 기존 완료Load 무쓰기, 새 R10 진행, 실패retry 무중복, 미지원 새 저장 원문보호, 사망 R01을 관련 시험으로 확인한다. 과거 golden fingerprint와 기존 완료receipt만 대표 확인하고 전체 조합을 재탐색하지 않는다.
4. 승인 아트→UI/월드/Host를 서로 다른 파일 소유로 통합. Editor·sync·빌드·Player는 통합자1명. 관련 시험과 실제 한 앱·대표 최대3화면으로 첫 출애굽기 진입→전투→정산/저장→새프로세스 재개를 확인한다.
5. 독립 코드/UI 리뷰·필수수정·관련 재검증·라운드 GC·commit/push·해당 SHA CI. 이후 R11→R12→R13→R14→R15 순서로 같은 사이클. 두 보스의 상태/예고/보상/Load는 해당 라운드에서만 추가한다.
6. 마지막 한 번의 대표 R09→R15 연속 확인. 기술 초기 HP/장비/직접 피해를 쓰면 자연완주와 구분한다. 성능·native·실물모바일을 실행하지 않았으면 NOT_RUN 유지. 레위기 자동 시작 없음.

## 작업 소유와 모델

제품 작성 상한5명, 불필요한 빈 배정 없음. 실제 사용 가능한 동시 슬롯에 맞춰 Core/기획과 아트부터 병렬화하고 Unity 세 영역은 준비된 뒤 나눈다. 상한5가 실제5명 가동을 뜻하지 않는다. 각 라운드 task packet에 정확한 허용 파일·산출물·검사 범위를 붙인다.

Sol은 기획·구현·일반독립리뷰, 좁은 파일조회는 도구 직접 또는 경량모델. Astra는 Sol로 미해결인 어려운 검증만. 사용량은 기존 `tools/record_model_usage.py`의 단계별 start/end 기록을 사용하고 실제 청구/절감률은 근거가 없으면 미계산이다.

현재 사용자가 지정한 Claude 제외 지시는 별도 재개 전까지 유지한다. 아트가 필요하면 기존 Codex 스크립트 픽셀 파이프라인으로 제작하고 Claude Design 실행으로 보고하지 않는다. 오늘18시가 됐다는 이유만으로 계정/도구를 자동 호출하지 않는다.
