# 창세기 개발 계획 — Unity 설치 전 선행 개발

상태: 사용자 "계획대로 진행해" 승인 후 R01 선행 코어 구현 중. 라운드별 GC 후 GitHub 업로드도 추가 승인됐다. 사용자 요청은 창세기 개발, 라운드별 GC, Unity 설치 연기다. 코어 상태는 docs/progress/R01.md에 기록하며 실제 게임·라운드 플레이가 구현된 것으로 표시하지 않는다.

## 확인한 환경과 변경 범위

- 개발 루트: 이 저장소(Bible-Survivor). 기존 main 초기 커밋은 b8b31de다. 이미 있는 docs/game-design.md 변경과 mobile-platform-plan.md를 보존한다.
- 현재 저장소는 기획 문서만 있다. Unity 프로젝트 식별 파일과 C#·씬·asmdef는 발견되지 않았다. Unity Hub/Editor는 표준 설치 위치에서 발견되지 않았고 Unity/dotnet/csc/mcs 명령도 PATH에서 발견되지 않았다. 다른 사용자 지정 설치 위치의 부재까지 단정하지 않는다.
- Unity 설치·계정·라이선스 변경은 이번 단계에서 하지 않는다. 순수 C#도 컴파일러가 필요하므로 기존 사용자 지정 SDK 경로를 먼저 확인하고, 없으면 프로젝트용 로컬 .NET SDK 설치를 구현 계획 승인 범위에 포함한다. 전역 PATH/셸 설정은 변경하지 않는다. 네트워크나 SDK 실행이 불가하면 코드 작성과 실제 컴파일 미실행을 구분한다.
- 서버 없음: 로컬 파일과 로컬 저장만 사용한다. 서버 재시도·외부 데이터 변경 시험은 해당하지 않는다. 사용자의 추가 지시에 따라 검증·독립 리뷰·GC 완료 후 공개 저장소 작업 브랜치에 push한다. 배포·merge는 포함하지 않는다.

## 구현 순서와 게이트

1. **선행 기반:** 순수 C# 코어·테스트·콘텐츠 데이터와 실행 가능한 로컬 시뮬레이션 검사 진입점을 만든다. UnityEngine/UnityEditor에 의존하지 않는다. 목표 Unity에서 사용할 수 있는 API 범위를 보수적으로 유지하고 실제 Unity 호환성은 후속 컴파일로 확인한다.
2. **아담 로직:** 3분 라운드, 첫 세 무기, 몬스터 3종의 데이터, 경험치·레벨업·일시정지·사망·라운드 전환·골드를 구현하고 자동 검증한다. 같은 라운드 내 작업 단위별 검사 후 독립 코드 리뷰와 R01 GC를 수행한다.
3. **Unity 전환:** 승인된 Unity 프로젝트 생성/연결 후 실제 이동·충돌·공격·UI·아트 임포트를 구현·검증한다. 이 단계는 Unity 설치까지 BLOCKED다. 아트 시안 02는 별도 진행 중이며 최종 에셋으로 승인된 상태가 아니다. 개발용 임시 표현과 최종 아트는 구분한다.
4. **모바일 선행 검증:** 첫 창세기 콘텐츠 확대 전에 터치 입력·안전영역·중단/복귀·저장·실기기 성능을 PC/Android/iOS별로 확인한다. 방향·지원기기·성능 예산은 별도 결정한다. 불가하면 해당 게이트는 닫힌 상태다.
5. **후속 라운드:** 앞 게이트가 통과하고 다음 구체 단계가 승인되면 아래 순서로 확장한다. Unity가 없는 동안 후속 라운드의 데이터 스키마·예산 무결성 검사는 준비할 수 있으나 해당 라운드의 전투 구현 완료나 플레이 통과로 세지 않는다.

## 담당 파일과 구조

승인 후 제안 구조:

- `src/BibleSurvivor.Core/`: 시간·웨이브·전투 규칙, 성장/보상/영구 성장 및 저장 모델. Unity에 의존하지 않는 단일 구현 담당.
- `tests/BibleSurvivor.Core.Tests/`: 실제 동작과 실패·복구 회귀 검증. 개발자가 작성하고 독립 리뷰어가 시험의 의미도 검토.
- `content/genesis/`: 라운드·몬스터·웨이브·보스·해금/보상 데이터. 안정 ID와 스키마 검증. 문서 수치를 임의 변경하지 않는다.
- `tools/`: 로컬 검증 실행 진입점. 누락 SDK/프로젝트를 성공으로 처리하지 않고 실제 종료 코드를 보존한다.
- `docs/harness/`, `docs/progress/`, `docs/retrospectives/`: 경계·검사·모델 계획, 단계 상태, R01~R09 회고와 근거 위치.
- Unity용 `Assets/`·`Packages/`·`ProjectSettings/`는 설치 전 만들지 않는다. 이후 Unity 어댑터/프레젠테이션 담당과 씬/프리팹 단일 작성자를 명시한다.

원본 기획은 기존 bible-survivors-docs 폴더의 최신 문서와 이 저장소 docs 복사본을 대조한다. 기존 변경을 되돌리거나 무관한 파일을 커밋하지 않는다. 공개 산출물에 개인 절대 경로·계정 정보·실행 원문 로그가 섞이지 않게 한다.

## R01의 수용 조건

1. 시드·시간 입력을 통제해 웨이브 경계와 총 생성 수/구성/XP를 재현한다. 동시 상한 때문에 지연되는 생성, 생성 마감 후 남는 예산의 처리와 프레임 시간 변화도 검증한다. 6210마리/원시 XP 18600이라는 9라운드 전체 데이터 합계를 검증하되 실제 처치량으로 보고하지 않는다.
2. 원시 XP와 보너스, 레벨 경계·대량 XP 획득, 무기/보조 슬롯, 중복 없는 최대 3개 선택·최대 레벨 제외를 시험한다. 후보가 모자랄 때의 처리도 원본 기준으로 정의한다.
3. 피해·방어·무적시간·정지된 시간, 사망과 완료 동시 발생 순서 등 미정 경쟁 조건은 구현 전에 좁은 결정 기록으로 고정하고 시험한다. 세 무기의 공격 수·주기·범위 데이터 검증과 실제 Unity 히트 판정 검증을 구분한다.
4. 완료 시 전체 회복과 장비/레벨/XP 유지, 사망 시 창세기 1라운드 초기화 및 영구 잔액/구매/해금 보존을 시험한다. 새 도전의 영구 강화 스냅샷은 중단 중 구매/환불로 변하지 않는다.
5. 저장은 schemaVersion·안정 ID·거래 ID·임시 기록/검증/교체·백업·손상/미래 버전 처리로 설계한다. 이중 선택/완료/재시도, 저장 실패로 결과를 모르는 경우, 앱 강제 종료·취소/뒤로가 기존 결과와 보상 후보에 미치는 영향을 시험한다. 실패 시 기존 저장을 보존하고 미확정 보상을 중복 지급하지 않는다.
6. 전투 중 영구 골드의 저장 주기와 강제 종료 후 전투 재개/롤백 정책은 기획에서 미정이다. 구현 전에 데이터 손실/중복 획득을 함께 방지할 구체 안을 제시하고 승인한다. 모바일 OS 종료를 사망으로 취급하지 않는다.
7. 핵심 회귀는 해당 동작을 제거/변경한 실제 변이로 시험 실패를 확인한다. 독립 코드 리뷰 후 높은 심각도 결함을 수정·재검증한다. 순수 코어 시험 PASS는 Unity 플레이 PASS가 아니다.

## 라운드별 GC 운영

각 라운드의 개발 사이클 종료/차단 시 R01~R09별 회고를 남긴다. 게임 실행 도중 매번 GC를 실행한다는 뜻이 아니다.

- 근거: 변경/시험/실패/사용자 교정·리뷰 결함·작업별 실제 모델과 재시도·관측 가능한 사용량. 없는 토큰/비용은 미측정이다.
- 분류: 도구 버그, 검사로 막을 수 있는 반복 오류, 판단 실수, 규칙 위반, 불필요한 위임/중복 실행, 잘못된 보고.
- 개선: 재현 입력→수정 위치→확인 방법을 갖춘 도구 개선안을 우선한다. 단순히 규칙 문장을 늘리지 않는다.
- 반영: harness-gc의 진단/적용 분리를 유지하고 사용자가 고른 구체 항목만 proposal/apply한다. "라운드마다 GC"를 전역 규칙 자동 변경 승인으로 확대하지 않는다. 결과와 보류 사유를 해당 회고에 남긴다.
- 유효한 코드 검증이 끝난 단계만 커밋한다. Unity 검증이 남았으면 선행 코어 단계와 게임 라운드 완료를 분리한다. 사용자 추가 승인에 따라 GC 후 작업 브랜치에 push하고 원격 SHA를 확인한다. 배포·merge는 하지 않는다.

## 모델·위임·실행 예산

확정 데이터 변환/무결성 검사는 경량, 일반 코어 구현/테스트는 표준, 저장·보상 무결성/난해한 실패는 고성능 후보로 판단한다. 실제 가용 모델을 실행 시 확인한다. 그래픽은 기존 Claude Design 지정 담당을 유지한다. 구현과 독립 리뷰를 별도 세션으로 분리하고 같은 코드를 두 구현자에게 중복 배정하지 않는다.

작업별 동일 프로필 재시도 최대 1회, 상향 최대 1회, 모델 실행 최대 3회 안에서 계획한다. 환경 부재는 상위 모델 호출로 우회하지 않는다. 실제 토큰을 측정할 수 없으면 시도/경과를 기록하며 추정 절감률을 주장하지 않는다.

## 현재 다음 단계

사용자가 **Unity 없이 진행하는 코어 기반·아담 로직 개발·로컬 SDK 준비·독립 코드 리뷰·R01 GC** 범위를 승인했으며 구현을 진행한다. GC 후 GitHub 업로드도 승인됐다. 창세기 전체는 위 로드맵으로 관리하고 Unity/모바일 게이트와 후속 구체 단계 승인을 건너뛰지 않는다. 화면 방향·최소 기기 등은 지금 사용자에게 모두 결정하게 하지 않고 해당 시제품 계획 시 제안한다.
